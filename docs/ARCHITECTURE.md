# 技术结构

V2 厨房管家由 Rust `steward` 调度，schema 15 增加本地任务、消息、草稿、增量检查与自动整理撤销表。前端旧补图和用量整理循环已退出统一启动流程；自动调用须通过管家设备、功能开关和免打扰检查，网络后重新检查身份及设置。手动调用不受免打扰限制。

周菜单草稿保存完整安排和正式菜单基线。预览使用内存副本，确认检查预览版本并复用 `Batch` 事务；业务回执确保崩溃恢复后不会重复提交。正式业务元数据使用 `steward_meta:*`，用户确认的食材规则使用 `ingredient_rule:*`，两者进入原有同步及云快照允许列表。本地协作表不上传；恢复保留草稿但重置主动执行身份。

自动整理使用独立撤销凭据，复用原事务变化及同步逆向重放，不进入普通用户撤销栈。预计复查日期与真实 `expires_on` 独立。首次记录保留源名称、源数量、源单位及规格估计标记，不能根据规范单位逆推实际包装。

Tauri 2 承载 React / TypeScript 界面，Rust 管理 SQLite、业务事务、网页读取、模型调用与凭据。浏览器演示使用独立 fixture 和客户端，不作为真实业务数据来源。

## 数据约束

- 生产数据库位于应用数据目录。开发与 release 当前使用同一 identifier，不得用 fixture 覆盖用户库。
- SQLite 使用外键、WAL、事务和版本检查。迁移前用一致快照备份；未知或更高版本数据库不自动重建。
- 数量以十进制文本保存，后端负责权威计算。粗略记录与未填写到期日正常计入库存分配；明确过期与未来购买日期仍按现有日期规则排除。前端数值预览和演示预测不替代生产结果。
- 常规编辑生成不可变配方版本，菜单引用特定版本；修改菜谱不能改变历史计划。显式全局撤销可反向应用整个原事务，仍有后续引用或同行改动时拒绝并回滚。
- 计划不扣库存。采购事实、入库和实际烹饪分别管理，重算需求不抹掉购买事实。
- 常备调料按备有 / 缺少管理，不按餐次扣减。移出列表后不会因旧菜谱再保存而自动复活，可主动重新添加。
- 库存删除保留历史引用，将批次数量置零并记录 `inventory_deleted:{id}` 业务标记，查询和需求预测排除已删除批次；标记与编辑属性撤销记录同事务入队，随云备份和同步传输。库存结构版本保持 13；多设备应更新至同一版本后使用新增编辑与删除。
- 自动分类使用前后端共享的常见名称规则；新增购买默认自动分类，已有未分类库存可一键整理，手工分类优先保留。不调用模型，也不改写食材名称。
- 食材头像由 `ingredient_images.rs` 自动查找，模型仅处理食材名、搜索词与候选元数据；下载限制为 Wikimedia 图片主机，优先有可复用许可的清晰本体照片。最多每批 4 个食材，缩放为 192px JPEG，通过 `ingredient_image:{id}` 保存压缩图片及来源、作者和许可，同事务进入同步队列及备份。网络期间不持有数据库锁；保存前检查厨房身份和原图，换图不修改批次数量。后台失败静默重试，手动换图失败保留原图。模型上下文移除图片二进制。
- 常备调料共用上述图片流程，使用 `seasoning_image:{规范名称}` 保存并同步；有品牌别名时按规范名称显示。图片后台扫描仅查询库存名称和调料，不读取菜谱大图。头像用带留白的圆角容器完整展示，调料右键头像可查看来源与许可。
- 行内数量和库位修改仍由原生事务、请求回执和批次版本校验保存；返回 `baseRevision`、新版本、库存批次和事件，不重传菜谱媒体。前端基线匹配时应用库存结果，否则重新读取权威快照；失败保留错误提示。相关 Tauri 数据库命令通过异步调度执行，避免阻塞桌面线程。其它编辑保持原有完整重读方式。
- 库存保留不可变事件。日期修正复用版本化校正事件，并保存旧日期供撤销；后续批次变化会阻止过时撤销。
- AI 在数据库副本试运行命令，确认后同事务提交。过时、重复或失败提案不能部分写入。
- 用餐与通用设置以 `preferences_v1` 保存在 `app_settings`；独立 IPC 保存，AI 操作命令不能修改。仅用餐人数与饮食描述进入模型上下文，修改默认值不重写配方或已有菜单。
- 业务事务同步记录实际行变化与允许的设置变化；操作组与业务一起提交或回滚，副本标识和队列不进入手动云备份。详见 [离线操作记录](SYNC_OUTBOX.md)。

远端操作必须匹配账户与空间，按全局序号应用；本机未确认操作在同一事务中回退并重放。业务原值、主键、允许的字段与外键检查不通过时整体回滚，保留队列与游标。详见 [同步说明](CLOUD_SYNC.md)。

## 发布边界

代码、锁文件、配置、迁移和合成测试属于源码。个人数据库、凭据、聊天、导入图片、日志、截图、原始设计参考及构建产物不进入版本控制。

项目版本在 `package.json`、`package-lock.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`、`src-tauri/tauri.conf.json` 保持一致；schema 独立演进。

## 全局撤销与图片编辑

schema 14 的 `local_undo_history` 保存本机用户事务的实际行变化，复用同步载荷压缩记录，最多 50 条并控制在约 64 MiB（保留最近一条）。重启后继续可用；后台自动补图和远端同步不入栈。撤销按原值校验并原子反向应用，包含新建配方版本、图片和烹饪事件；原始载荷保留为本机撤销凭据。正常不可变触发器仅在明确撤销事务及同步重放内暂时挂起，恢复后继续生效。撤销产生 schema 14 的显式 `undo` 同步操作，普通同步仍禁止改写不可变历史。本机撤销栈不上传，云备份和恢复会清空它；升级不追溯旧版本操作。不提供重做。

菜谱图片在编辑草稿中压缩、替换和移除，保存后形成配方新版本，原菜单仍使用绑定版本。AI 封面只处理菜名与图片偏好，通过 Commons 查找可复用的成品照片并保留署名和许可，返回参考图供保存前查看；不伪称原作者实拍。步骤图按步骤编号保存，删除文字步骤会同步移除/重排对应图号。

`RecipeMediaEditor` 分别用于封面和各步骤末尾的图片编辑，`RecipeStep` 根据图片实际宽高安排文字与图片，保留原图比例。`navigation.tsx` 在离开时记录页面滚动位置，在布局更新时恢复目标位置；新路由默认为顶部，不再由菜谱页维护另一套滚动逻辑。首页 `nextMealDishes` 先选最近未过时餐次，再按计划顺序收集同日同餐的未完成菜，界面最多预览两道。

## 食材统一与文字烹饪记录

`ingredientStandards.json` 由 TypeScript 和 Rust 共用，规范常见名称与单位。`ingredient_standard` 在新建/编辑菜谱、入库和手动采购入口统一数据；原始来源文本及旧行 ID 保留，库存和采购采用同类匹配与单位系数计算。历史采购行保持其原单位，通过换算分配需求，其他同类已买未收货数量共同抵扣，避免重复购买。包装和计件重量是常见规格估算，非实测净重。

`ingredient_resolver` 在后台取一个待整理配方、释放数据库锁后调用模型，将原文用量及无法直接换算的库存单位整理为 `ingredient_resolution:<revision>`。校验只允许该配方食材、不得遗漏食品；明确且可换算的原配方用量由程序保留。新估算条目与依据单独缓存，不改写不可变配方版本。前端启动、业务变化、联网及 AI 设置变化后自动唤醒。后台事务不进入用户撤销栈，但随同步传输。离线或失败保留源文本，稍后重试。

`cooking_ai` 接受独立烹饪记录，只返回现有批次 ID 及其原单位消耗。原生端合计检查超量、版本变化并在保存前重新预览；实际扣减仍统一走 `CompleteCooking` 原子事务。文字记录存于 `cooking_record:<session>`，手记同时写入菜谱 `cooking_notes`（以 session ID 关联），明确撤销烹饪时一并撤销手记与消耗。两类设置已加入同步和云快照保留清单，无新增表结构。

助手提案先经 `assistant_commands` 兼容常见字段拼写及数值类型，再使用原有严格命令验证与内存数据库试执行。不能创建 ID、丢弃业务字段或在兼容环节执行写入。后台图片事务只改外观，不增加业务修订号；提案生成期间业务变化会重新取上下文，网络/服务短暂失败最多自动重试一次。鉴权失败仍明确报错。

## 品牌资源

`public/brand.svg` 是按用户提供的鱼形厨师帽/刀叉标识重绘的矢量源文件，外边透明、图形使用砖红与米白两色。侧栏、设置与关于页以及网页 favicon 共用该文件。使用 `npx tauri icon public/brand.svg --output src-tauri/icons` 重新生成平台图标，Windows 包使用其中的 `icon.ico`；修改图标后必须重新构建发行包。`build.rs` 显式跟踪 `icon.ico` 与 `icon.png`，避免 Cargo 复用旧的 Windows 资源库。
