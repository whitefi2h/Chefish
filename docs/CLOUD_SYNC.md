# 账户与多设备同步

2026-10-26：已接通邮箱账户、首次厨房连接、后台双向同步、离线补传和冲突处理。原生 SQLite、云端权限、界面与真实 Firebase 均有独立测试；两台实体电脑和用户实际网络下的体验仍需实用观察。免费 Firebase 项目为 `chefish-kitchen`，未使用 Cloud Storage、Functions 或启用计费。

## V2 兼容性

V2 数据库为 schema 15，同步设备应一起升级至 V2.0.0。云端规则需接受 schema 15；本轮规则与原生双库模拟器测试通过，但 2026-10-28 发布时 Firebase CLI 凭据已过期，生产规则更新尚待重新登录后部署。该状态与本地功能验收分开记录，不能把模拟器通过视为生产更新已完成。

## 使用

打开左下角“我的厨房 → 账户与云端”，登录并验证邮箱。

- 账户尚无厨房时，选择“用本机厨房开启同步”。程序上传当前厨房作为初始备份，再同步上传期间产生的新操作。
- 账户已有厨房时，选择“连接云端厨房”，下载检查初始备份，确认后连接。替换前保存本机安全备份，本机聊天、模型密钥和通用设置保留。
- 连接后自动同步，支持“立即同步”和暂停。断网可继续编辑，联网、窗口重新获得焦点或下一次后台检查时补传。程序关闭期间不运行后台任务。
- 顶部显示同步状态；错误与冲突可点击查看。冲突会暂停，保留本机当前内容。选择“备份本机并保留云端”会先完整备份，再撤销这台电脑**全部尚未同步的操作**并拉取云端。也可暂停并先导出本机备份。

登录和退出本身均不替换厨房。当前厨房如果关联其他账户，界面显示原归属；上传备份与自动同步受原生归属检查保护。需要把厨房复制到新账户时，必须明确确认，复制前留存安全备份。原账户云端数据保留。

手动云备份独立保留某个时刻的厨房。确认整库恢复后，本机自动同步连接会重置；再次连接时需明确选择，避免把恢复后的旧内容直接上传为新操作。

## 同步范围

| 内容 | 处理 |
|---|---|
| 菜谱、封面与步骤图、历史配方、分类、收藏和灵感 | 同步实际对象 ID 与版本；图片随实际行载荷分块传输 |
| 库存、事件、菜单、采购、收货、烹饪与手记 | 整个事务为一个操作组，失败时整体回滚 |
| 默认人数、口味、忌口、厨具 | 同步四项用餐偏好 |
| 采购备忘、调料缺货/隐藏、批次删除标记与属性撤销原值 | 同步允许的业务设置 |
| 聊天、启动页、发送快捷键、自动备份开关 | 各设备保留自己的内容 |
| 模型密钥、Firebase 凭据、未知设置字段 | 不进入同步载荷与云备份 |

云端按账户隔离，要求验证邮箱。数据没有客户端端到端加密。登录凭据由 Firebase SDK 保存在 WebView 存储，模型密钥继续保存在 Windows 凭据管理器。

## 顺序、重试与冲突

SQLite schema 13 新增账户连接和已应用操作回执，升级前保存 `pre-v13-*.sqlite3`。本地事务队列见 [离线操作记录](SYNC_OUTBOX.md)。

账户只有一个厨房空间与一份不可变初始备份。云端路径：

| 路径 | 内容 |
|---|---|
| `users/{uid}/sync/head` | 空间、初始备份、全局序号与末次操作 ID |
| `users/{uid}/sync_operations/{uuid}` | 不可变操作清单、序号、载荷哈希、分块引用 |
| `users/{uid}/sync_blobs/{sha256}` | 压缩操作载荷的 256 KiB 分块 |
| `users/{uid}/backups/{uuid}`、`chunks/{sha256}` | 手动备份和初始厨房备份 |

先上传并校验分块，再在同一个 Firestore 事务中发布操作并将全局序号增加一。规则要求清单与 head 互相对应，禁止跳号、独立推进游标、改写或删除历史。客户端校验每块和整体哈希，原生层校验格式、结构版本、表/列允许列表、主键和外键。

每次拉取按序处理。原生层在一个 SQLite 事务中倒退本机待上传操作、应用云端操作、再重放剩余本机操作；成功后才移动本机游标、清除本机已确认操作。重放使用已保存的行结果，不重新执行会生成随机 ID 的业务命令。不可变历史只允许远端插入，临时回退所需的触发器调整与业务重放在同一事务中完成。

两边修改不同记录时可以继续合并；同一行、同一业务设置或唯一性约束冲突时保守暂停，即使修改的是同一行的不同字段。失败回滚全部业务变化，不移动游标，不丢弃队列。重复下载和上传确认丢失以操作 ID、哈希及已应用回执识别，不重复扣库存。

首次上传在同一数据库锁内取快照与本机队列水位，只清除该水位之前的操作，上传期间的新编辑留在队列。初始备份一经建立就不自动替换；新设备恢复它后继续拉取完整操作历史。

## 传输容量与保留

单份原始快照与单项操作载荷上限均为 512 MiB，这是应用校验上限。快照按 256 KiB 原始字节 gzip 压缩，操作载荷先压缩再分块；base64 文档保持在 Firestore 单文档上限以内。分块与清单均不可变，相同内容允许重试。大载荷与分块数组禁用无用索引，序号与备份时间保留查询索引。

当前不提供云端占用统计、操作历史压缩、旧快照删除或垃圾回收。免费额度耗尽会显示错误并保留本机队列；不要把 512 MiB 应用上限当作免费容量承诺。图库增长时需安排保留策略。当前没有静默启用付费服务。

临时文件通常随传输释放；强制结束可能留下缓存。整体云备份先检查哈希、SQLite 完整性与外键，再生成预览；实际替换沿用既有在线备份与回滚流程。

## 构建与部署

本机构建使用 `.env.local` 的 Chefish 独立公开 Web App 配置；其他开发者需参考 [`.env.example`](../.env.example)。不提交本机配置、管理员凭据或私钥。参考项目 `E:\zenfish` 保持只读，没有复用其 Firebase 项目与凭据。

```powershell
.\node_modules\.bin\firebase.cmd deploy --only firestore --project chefish-kitchen
npm run tauri build -- --bundles nsis
```

认证使用普通 Email/Password 与邮箱验证；无需升级 Identity Platform。CSP 只允许必要的 Google API 主机。

## 验证

```powershell
cargo test --manifest-path src-tauri/Cargo.toml -j 1
npm test
npm run test:sync:emulator
npm run test:ui
```

`test:sync:emulator` 先构建原生测试程序，再启动 demo 项目模拟器。测试桥只创建自己的临时 SQLite，不能接收任意数据库路径，不包含在发行程序中。双库联测覆盖含图片初始备份、原生恢复、并发离线操作、重启、云端提交但确认丢失、同一批次冲突及明确选择云端后的收敛。Rust 测试另覆盖采购、烹饪与撤销完整操作组、私有字段拒绝、偏好隔离和恢复前备份。界面测试使用服务替身，不能替代真实云传输。

真实云端检查需显式设置 `CHEFISH_LIVE_CLOUD_TEST=1` 与 `CHEFISH_NATIVE_SYNC_TEST=1`，运行 `npx vitest run tests/firebase-live.test.ts`。测试只允许 `chefish-kitchen`，使用生成的临时邮箱账户、两份隔离原生数据库和合成图片，经过真实 Auth/Firestore 完成初始备份与双向操作传输，并精确清理生成的账户和文档。无需发送邮件；仅合成身份通过管理 API 标记邮箱已验证。普通测试默认跳过真实云检查。

最新证据与边界见 [同步验证记录](sync-validation.json)。真实邮箱收信、Windows WebView2 内个人账户登录、两台实体电脑和长时间运行仍未作为自动测试完成；没有上传用户现有厨房。
