# 粗略计量模式：代码审查与实施方案

日期：2026-11-20。当前代码版本：2.3.12，数据库 schema：18。本文件是方案，不代表功能已实现或通过验收。

## 1. 产品边界

目标是减少记账负担。精确模式继续保留，粗略模式可在统一设置中开启；粗略模式的库存和饭后记录不要求填写克数或个数；采购清单仍显示食材和具体所需数量，但完成采购只需勾选。菜谱本身的配方用量仍保留，因为做菜和人数换算仍需要配方。

建议正式版本使用 2.4.0：当前已发布到 2.3.12，2.3.0 已经发布过，复用会被 SemVer 更新比较视为降级。若保持 2.3 系列，可使用尚未占用的后续版本，但本功能涉及数据结构变化，2.4.0 更便于识别。

三档定义：

| 显示 | 含义 | 对规划的影响 |
|---|---|---|
| 少／缺乏 | 有剩余，但等于或少于一顿的量 | 优先关注补充；不能因此断言连一顿也做不了 |
| 中／充足 | 至少够两顿，尚未达到用户认为大量的程度 | 可优先用于近期菜单，但不能保证够整周 |
| 多／盈余 | 用户判断存量较大 | 优先消耗，减少重复补货；不代表无限供应 |

“一顿”指当前家庭通常用餐人数下，这种食材一次作为菜中材料的常用量，不指一个人的份量。标记时记录参考人数，之后修改默认人数不重写过去的判断。人数明显变化时，规划降低对可用量的确定性。

**用完必须独立于三档。** 拉杆只设少、中、多三个停靠点，另设“用完了”操作。用完后的食材不参与可用库存、临期提醒和配菜搜索。还需允许迁移阶段“尚未估计”的状态，不能把未知库存当成缺乏、充足或空库存；它不是正常使用中的第四档。

## 2. 当前程序中必须兼容的位置

| 范围 | 当前实现与问题 | 改造要求 |
|---|---|---|
| 库存模型 | `inventory_lots.amount_decimal`、`unit`、`precision`；`InventoryLot` 继承数值用量；已有 `precision=rough` 仍保存数字，新增入库页当前也会标 rough | 新增独立的计量类型与档位，不能复用 precision 解释成三档 |
| 库存操作 | `src/Inventory.tsx` 中入库、详情、列表加减、删除；`db/inventory.rs` 校验十进制数量并写数值流水 | 直接新增食材时可选档位；清单勾选入库不要求选档；数值加减改为三档拉杆；拖动预览，松开后提交一次；键盘可操作 |
| 首页、提醒 | `domain/inventory.ts` 以 quantity>0 筛选；首页、调料库存与库存页存在不同展示路径 | 共用“有库存/用完/未知”的领域判断，不能继续用旧数字决定是否有货；过期、临期独立保留 |
| 采购计算 | `db/shopping.rs` 按日期、单位换算、批次余量依次抵扣，生成 required/covered/remaining | 粗略库存不得产生伪精确的 covered/remaining；增加状态型采购判断 |
| 购买、入库 | `NativeShopping.tsx` 要求实际购买数量，支持购买、入库、撤销，助手也有“买好了”快捷路径 | 清单显示食材和所需数量，勾选即完成采购及入库；日期为勾选当日，新批次默认充足，不弹填写表单 |
| 烹饪完成 | `Cooking.tsx`、`db/cooking.rs`、`cooking_ai.rs` 用批次数量扣减，支持文字记录与撤销 | 手动拉杆默认展开且优先；AI仅辅助未手调项目；精确消耗与档位调整在同次事务保存，不依赖数字或AI才能完成 |
| 菜单与缺料 | 周菜单、Planner 缺料预览、Dashboard、StewardInbox 使用采购预测 | 区分“建议补货”“库存量不确定”“已有库存”；不能把充足解释为所有餐次都足够 |
| 菜谱与导入 | 菜谱的食材量、标准人数、导入后的用量整理均为配方数据 | 配方数字不变；仅库存记账与采购抵扣分支改造 |
| AI | 通用助手 context 直接带数值 snapshot；烹饪提示词要求 quantity；管家维护和周菜单也消费库存 | 提供带类型的库存上下文、档位命令与预览；所有入口使用一致规则 |
| 历史、撤销 | 库存与烹饪流水不可修改；撤销恢复数量、位置与版本 | 记录计量类型、档位、可用状态的前后值；新事件不伪装为克数变动，历史旧流水原样保留 |
| 同步与设置 | `db/sync.rs` 有明确表白名单；preferences 为严格字段反序列化，部分设置有单独同步策略 | 增补新表及设置策略、字段合并、重放、强制替换；不把新增字段直接塞入旧版设置导致旧客户端报错 |
| 备份和云端 | schema=18；云备份清理 app_settings 有白名单；Firestore 两类 manifest 的 schema 上限为18 | schema升19，更新恢复校验、完整快照与规则上限；新数据不得在快照中被裁掉 |
| 复制、演示、辅助入口 | 采购复制、助手操作差异预览、演示 model.ts 仍计算并展示数量 | 共享带计量类型的格式化与判断，不只修原生数据库页面 |

## 3. 数据方案

建议采用“档位是真实记账数据，数字不是档位的编码”的方案，不把少、中、多写成 100g、300g、1000g，也不把数字字段改成中文。

为避免破坏已有数量流水，新增 schema 19 的类型化库存状态和事件扩展表：

- `inventory_measurements`：批次 ID、计量类型 exact/level、可用状态 present/empty/unknown、档位 low/adequate/surplus（可空）、标记时参考人数、标记来源 manual/ai/purchase/migration。使用同一批次 version 管理并发，不另造独立的冲突版本。
- `inventory_measurement_events`：关联统一库存/烹饪事务，保存计量状态 before/after。精确流水继续走旧数值逻辑；档位变更走新逻辑，二者由统一命令路由。
- 历史数值保留以便查看旧记录。对已经切成 level 并发生变动的批次，旧数字明确标为历史值，不能继续用于可用量、采购或AI判断。新建 level 批次的旧数值字段可保留内部占位以兼容旧表非空约束，但所有业务分支必须按计量类型读取，且不得将占位数对外暴露成数量。
- 新设置建议单独的版本化记录 `inventory_measurement_settings_v1`，包含默认计量方式，避免改写旧版严格解析的 preferences_v1。它是厨房共享的记账设置，纳入同步和云备份。
- Rust IPC 和 TypeScript 使用区分类型：exact 携带数量及单位；level 携带档位和可用状态。UI、AI和采购不再直接假设所有批次都有可用数字。

保留批次维度有助于维持已有冷藏/冷冻位置、购入日期、到期时间和撤销能力。粗略模式库存页可按食材归组、展开批次；拉杆调整实际对应批次。**不同批次档位不能取最大值或直接相加当作精确总量**；分组显示批次状态，规划按不确定库存处理。后续如要增加整种食材一键调整，需要明确调整哪些批次，不能暗改所有日期和位置不同的批次。

数据模型实现时集中梳理所有 quantity>0、库存求和、单位换算入口，建立统一 stock availability 函数。只新增字段而保留旧计算方式会导致“界面显示缺乏，后台却认为有500g”的错误。

## 4. 开启、关闭和旧数据转换

1. 默认保持精确模式；统一设置中增加“库存计量方式”，使用现有行布局和开关/选择控件。
2. 开启粗略模式不立刻批量改写旧库存。保留当前精确记录和历史，向导允许按食材快速设置档位，未判断项不伪装成某个档位。
3. 有可靠的常用配方及家庭人数时，可给出档位建议，用户可调整；不能按所有食材统一的克数阈值自动分档。多档中的“盈余”主要以用户判断为准，不强行设成同一个重量。
4. 滑杆提交粗略状态后，该状态成为当前事实；旧数值不再具有实时库存含义。
5. 切回精确模式时，未发生粗略变更的原精确记录继续可用；发生变更的批次保留档位并提供“补填当前数量”入口。补填之前支持混合数据，不能恢复旧数字冒充当前数量，也不要求一次补齐所有食材才能使用程序。
6. 修改模式本身不等于购买、消耗或用完，不新增虚假的采购/烹饪流水。迁移前使用现有自动安全备份路径。

## 5. 采购与周菜单规则

粗略模式保留“买什么”的核心价值，减少假精确的数量结论：

- 用完：列入待买。
- 缺乏：本次菜单需要时列入建议补充；用户知道剩余够这一顿时可取消。
- 充足：短期使用优先选用；一周多次安排该食材时显示需核对，不计算虚构的剩余克数。
- 盈余：优先消耗，默认不重复补货，但不能忽略人数变化、过期或大量重复安排。
- 未估计：标为需核对，不直接判有货或缺货。
- 精确批次仍能计算已知抵扣，但只要该食材还涉及粗略批次，就不能把算出的精确部分包装成最终缺口。
- **采购页以食材＋所需具体数量为主**，例如“鸡蛋 6个、玉米 2根、排骨 500g”，保留清单式复选框，勾选即完成。复制清单也包含这些数量，不以状态文字替代数量。
- 清单数量来自菜谱用量按计划人数汇总，精确且可靠的库存部分可以抵扣；粗略库存无法精确抵扣时，列出需补充餐次的配方参考量，不把它称为计算精确的净缺口。采用一个简短列标题“所需数量”，不在每行堆解释。未明确用量时保留原始量词或“适量”，不能编造数值。
- **勾选同一事务完成采购记录与新批次入库**：采购日期及入库日期采用设备本地勾选当日（跨午夜时以提交时为准），记录量为清单建议量，来源标为清单默认，不伪称用户称量；库存批次的当前计量类型为level、默认充足。无需用户填写数量、日期、库位、保质期或再次确认入库。
- 购入动作要留下独立新批次，不覆盖既有批次的日期或状态；同种食材原有盈余批次不能因补货而被改成充足。重复点击、网络重试使用同一采购动作标识，不能重复入库。清单完成状态以采购记录维持，不能因“充足没有精确克数”而立即重新出现为待买。
- 勾选后沿用原列表的已购买状态展示，不另改成划线式清单；需要撤销时复用既有采购撤销能力。若入库后已被烹饪使用，不能通过取消勾选直接删除或覆盖后续记录，应提示无法直接撤销。
- 新批次库位先为“未指定”，真实保质期为空，标记需要整理；下一次AI整理自动补推测库位和预计复查/到期提醒，不阻塞本次勾选。预计日期与真实包装有效期分别存储，界面标“预计”；AI估算不能伪造包装保质期。无AI、离线或识别失败仍完成采购，保留待整理状态，下次再处理；不得因失败要求补填。
- 对粗略采购自动整理默认允许合理估算，不另让用户开启隐藏的allowEstimates开关。只补空缺或仍有效的自动建议，永不覆盖用户后来手填的日期、库位和手调档位；已有更严格的用户禁用自动整理偏好仍应尊重。
- 周菜单继续执行 v2.3.11 的本地真实菜谱优先、库存组合搜索下厨房、真实评分优先策略；档位用于优先级和补货判断，不用于编造食材用量。

## 6. 饭后记录与AI

**手动优先，AI次之。** 完成烹饪面板默认展开本餐食材拉杆，先让用户直接调节，支持保持不变、调档和“用完了”，不要求逐项必填。文字记录与“AI识别”作为次级入口，手记选填。
- 点击“确认完成”直接保存当前拉杆状态，不自动调用AI，不等待模型；没有手调或明确AI建议的食材保留当前状态，不自动按菜谱降档。
- 每个食材记录本次会话manualTouched。用户操作拉杆、点击档位标签、选择用完或恢复原档位，都视为手动选择；AI只能填未手调项目。AI处理期间用户仍可调拉杆，返回后再按最新manualTouched过滤，不能覆盖请求发出后新发生的操作。
- AI已给出的结果仍可被手动覆盖；再次识别也不能覆盖本次手动值。需要撤掉手动保护时提供明确的“重置本次调整”，不因修改文字悄悄解除。
- 识别失败显示简短提示即可；完成按钮保持可用。后端同样校验手动优先的合并结果与批次版本，不能仅靠模型提示词承诺。
- 日期、人数及烹饪记录继续保存；AI不以配方参考量推翻用户直接指定的剩余档位。

示例：

| 用户输入 | 建议结果 |
|---|---|
| 排骨用完了，玉米还够两顿 | 排骨标记用完；玉米标记充足 |
| 青菜只剩一点 | 青菜标记缺乏 |
| 刚买了一大袋土豆，现在很多 | 土豆建议盈余；需结合是购买完成还是仅聊天来生成提案 |
| 鸡蛋用了一个 | 精确批次按数量扣减；粗略批次只记录这次用了一个，不能仅凭此断言剩余档位 |
| 用了一点，还是很多 | 保持盈余，并记录文字 |
| 今天没用排骨／排骨没全用完 | 不把它当成清空库存 |

粗略档位是区间判断，**不能每做一顿就机械降低一档**：充足减一顿后可能仍然充足，多也不等于固定三顿。用户明确说剩余状态时自动生成对应变更，模糊记录可保留原档位并照常完成保存，不每次强制追问。

AI兼容改造：

- 通用助手、管家维护、周菜单与烹饪共用类型化库存上下文；粗略批次不提供失效的旧数量。共享数量格式化不应再次泄漏历史数值。
- 更新 `assistant_prompt.txt`、`steward_plan_prompt.txt`、`steward_maintenance_prompt.txt`、`cooking_record_prompt.txt`，同步调整内嵌提示词、上下文构建、确定性快捷意图和命令预览，不只改一份提示词。
- 粗略烹饪输出 `levelChanges`，与已有 `consumptions` 分开。每项带真实批次ID、预计版本和目标状态；不要求模型生成伪造 quantity。
- 明确来源优先级：本次用户手动拉杆/用完选择 > 本次明确剩余状态的AI识别建议 > 当前有效库存 > 配方参考；否定、修正和批次范围继续生效。
- 先预览，再随“确认完成”在同一事务中写烹饪记录及档位变更。识别失败依旧可保存文字记录，不阻止完成；AI不能借由聊天直接改库存。

## 7. 同步、备份和升级

- 新表加入 `db/sync.rs` 的同步白名单、捕获和重放；档位、可用状态与计量类型作为同一状态原子更新，不按互不相关字段合并。
- 同一批次两端同时改档位，沿用现有同步版本合并机制；跨 exact/level 的切换作为同一次状态变更。未同步操作和强制替换路径都要验证。
- schema 19 新增结构后，更新 CURRENT_SCHEMA、备份校验、完整快照清理白名单、云端 manifests 版本限制以及 Firestore 规则；本地规则检查不等于生产规则已部署。
- 旧版客户端不能继续写新计量厨房：旧程序只理解数字，会覆盖或误扣。新schema快照由旧程序拒绝；增量同步还必须加入明确的版本/能力门槛，不能只指望完整快照校验。旧客户端至少应安全停止写入并提示升级，若现有协议无法可靠阻止，先发布可识别能力门槛的过渡版，再开放粗略模式。
- 完整备份、云恢复、重新绑定、强制替换均保存档位、类型、参考人数和历史；恢复前仍用现有安全备份机制。新业务设置不应误当成本设备专属设置而在云恢复时丢弃。

## 8. 分阶段实施与验收

1. **状态契约与迁移**：实现类型化库存、schema19、兼容读取、命令及前后状态事件；先覆盖精确/粗略混合、旧记录升级和撤销。
2. **库存与设置UI**：统一设置开关、旧库存转换预览、三档拉杆、用完操作、粗略入库；首页及提醒统一判断。
3. **采购与规划**：食材与所需具体数量清单、勾选原子采购入库、勾选当日日期、充足新批次、AI下次补估库位/日期、复制清单、周菜单及缺料预览。
4. **饭后记录与AI**：默认展开手动拉杆、manualTouched优先与AI异步结果合并、levelChanges、提示词及快捷意图适配、事务保存与撤销；完成不自动调用AI。
5. **多设备和交付**：同步/完整恢复/旧客户端门槛、规则部署与回读、隔离UI预览，最终统一构建、签名、发布。

关键验收包括：

- 精确模式旧行为不变；三档界面不泄漏库存数字，配方数字仍可用于做菜。
- 缺乏、用完、未估计不会混淆；过期与临期规则正常。
- 模式往返不恢复失效数量、不凭空增加库存；修改默认人数不重写历史。
- 粗略采购不把未知库存视为0或无限；一周重复用料不承诺精确足够。
